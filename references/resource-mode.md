# Экономный режим фоновой работы

Режим уменьшает параллельность и приоритет собственных задач SuperDJ, чтобы оставить компьютеру больше возможностей для другой работы. Он включается явно; без включения сохраняется прежняя политика допуска и очередей. Музыкальные алгоритмы, модели, точность вычислений, качество экспорта и проверки сведения не переключаются на упрощённые варианты.

## Включение и откат

```text
superdj resource-mode on
superdj resource-mode status
superdj resource-mode off
superdj resource-mode restore
```

`on` сохраняет профиль в поле `resource_limits` частной конфигурации `~/.cache/superdj/runtime.local.json`. `status` выводит только этот профиль, без остальных личных настроек. `off` отключает его для следующих запусков. `restore` отменяет последнее изменение только этого поля; остальные изменения конфигурации сохраняются. Если поле после команды было изменено вручную, откат отказывается его перезаписывать. Для изменений используется ограниченная по времени блокировка и атомарная запись с проверкой, что конфигурация не была изменена другим писателем.

Текущая сборка сохраняет политику, выбранную при её запуске. Команды не прерывают задачи и не расширяют ограничения уже запущенных процессов. Ограничитель ресурсов, установленный отдельно от проекта, остаётся под управлением пользователя: SuperDJ не меняет его файлы, автозапуск или настройки.

## Параметры по умолчанию

```json
{
  "resource_limits": {
    "enabled": true,
    "cpu_cores": 4,
    "model_jobs": 1,
    "cpu_jobs": 1,
    "math_threads": 1,
    "memory_headroom_gib": 4.0
  }
}
```

Это фрагмент для добавления в существующую конфигурацию, а не замена всего файла. Можно настроить значения: `cpu_cores` 1–64, очереди 1–4, `math_threads` 1–16, запас RAM 0–1024 GiB. Параметры очередей конкретной команды могут уменьшить эти пределы. Завысить их относительно включённого профиля команда не может. Более строгие унаследованные ограничения CPU и численных библиотек сохраняются.

Нейросетевая обработка и CPU-подготовка не перекрываются по фазам. На существующие модели и выбранные GPU это не влияет. Проверенный постоянный кэш по-прежнему требует явного включения; режим не включает, не удаляет и не перемещает его. Для новых временных файлов сохраняется настроенный `scratch_root`, а явно заданный пользователем `--work` остаётся явным выбором рабочей папки.

## Что ограничивается системой

В Windows процесс команды SuperDJ использует до четырёх логических процессоров из уже разрешённой ему маски. Он получает Idle-приоритет CPU и Very Low приоритет I/O. Дочерние процессы наследуют маску CPU и приоритет; собственные нейросетевые рабочие процессы дополнительно настраиваются по удерживаемым дескрипторам `Popen`. Сканирование произвольных процессов и изменение других приложений не выполняются.

При использовании SuperDJ как Python-библиотеки профиль ограничивает очереди и численные пулы внутри области выполнения, а также её собственные рабочие дочерние процессы. Маска CPU и приоритет процесса приложения, встроившего библиотеку, не меняются. Пулы, уже загруженные приложением, ограничиваются через `threadpoolctl`, когда это поддерживается; окружение также ограничивает новые пулы. Отчёт отмечает недоступность управления пулом.

На Linux собственный процесс команды и сам нейросетевой интерпретатор применяют доступную маску CPU и `nice=19`. Родитель не перенастраивает дочерний процесс по числовому PID: это исключает гонку с завершением и повторным использованием PID. Понижение приоритета I/O этой реализацией вне Windows не выполняется. На других платформах неподдерживаемые операции отражаются в отчёте; ограничения очередей и потоков сохраняются. На Windows с несколькими группами процессоров маска ограничивается текущей группой. Ограничения не расширяются при выходе из области: для полного снятия собственных нативных ограничений запускается новый процесс после `off`; ограничения внешнего ограничителя при этом сохраняются.

Основания: [маска CPU и наследование](https://learn.microsoft.com/en-us/windows/win32/api/winbase/nf-winbase-setprocessaffinitymask), [классы приоритета процессов](https://learn.microsoft.com/en-us/windows/desktop/api/processthreadsapi/nf-processthreadsapi-setpriorityclass), [значения приоритета I/O](https://learn.microsoft.com/en-us/windows-hardware/drivers/ddi/wdm/ne-wdm-_io_priority_hint). Настройка I/O процесса использует системные `NtSetInformationProcess` / `NtQueryInformationProcess`; их отказ явно фиксируется, а не считается успешным применением.

## RAM и проверка результата

Запас RAM — консервативная оценка допуска до тяжёлой работы, а не резервирование памяти или жёсткая квота дерева процессов. В `make`, `render` и `run` при включённом профиле тяжёлая задача не начинается, если измеренной свободной памяти за вычетом запаса недостаточно даже для одной полной задачи по оценке исходных записей. Отдельные команды анализа и произвольные SDK-вызовы не получают этой оценки полного набора исходников автоматически; область `execution` проверяет минимальный запас до создания своих рабочих процессов. Давление памяти может измениться после проверки. Режим не гарантирует отсутствие задержек других приложений, не задаёт лимит MB/s и не устанавливает максимальное число процессов. Он не очищает рабочие наборы и не завершает процессы ради освобождения RAM.

Отчёт выполнения содержит запрошенные и фактические очереди, профиль и результаты нативного применения: CPU, класс приоритета, I/O, ошибки неподдерживаемых операций. Неполное применение не описывается как полный успех. Сам профиль не запускает службу, таймер, автозапуск или фоновый монитор. Проверки ритма, полной игры 3–4 минуты, мастер-записи и декодированного FLAC выполняются как прежде.
