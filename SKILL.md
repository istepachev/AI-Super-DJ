# AI Super DJ

Deliver listenable audio, retaining originals and recording actual processing. One input file means enhancement and mastering; several files or a folder mean a mixed set. Use `superdj make` on a prepared workstation. Read [README.md](README.md) for commands, [references/workflow.md](references/workflow.md) for detailed checks, and [THIRD_PARTY.md](THIRD_PARTY.md) before changing a backend.

Optionally read private `~/.cache/superdj/runtime.local.json` for workstation paths. Keep audio, playlists, external model weights, private fitted profiles, caches and reports outside the source repository; only explicitly published portable parameters and aggregate benchmarks belong in it. Installing instructions alone does not install engines or weights. For first installation or a friend's reproducible DJ Zhilin setup, read [references/friend-setup.md](references/friend-setup.md). A fresh runtime uses ordinary F/SYNC; `default_style: zhilin` explicitly selects DJ Zhilin for subsequent `make` calls. Do not infer another workstation's default from this machine's private config.

## Preserve musical intent

Keep a supplied order (`fixed`, or `make --keep-order`). Otherwise propose a sequence using harmony, tempo, energy and transition regions. Respect locked positions, approved cues and protected ranges; do not silently omit tracks. A requested count, such as twenty tracks from a larger folder, requires an explicit selection manifest before rendering: `make` consumes all eligible folder inputs after history filtering and does not implement a count limit. For requested random selection retain its seed and selection in the private manifest.

For ordinary automatically ordered sets prefer a slower, lighter start and a faster, denser, bassier finish. Use the existing `build` development; a long set can use `wave` for a climb, breathing valley and another climb to the strongest finish. The planner applies position preferences to native BPM, measured intensity and bass, alongside transition feasibility. Treat these as a musical arc, not a requirement to increase every next track or force a playback-speed change. Use gain-invariant sound descriptors rather than file loudness for intensity/bass; they remain engineering proxies. Missing measurements contribute no guessed preference. Preserve explicit order and endpoints ahead of the arc.

For a requested Harmonize-style ordering experiment, use `harmonize` and `harmonize-compare`. Read [references/harmonize.md](references/harmonize.md). Fuzzy and Mood have different directed key rules; preserve every source and lock. Compare identical analysis before attributing differences to ordering. Freeze the existing profile on new files before fitting; recompute connected source cohorts when combining archives and hold out every linked old/new order/mode variant together. A new order of trained sources is not an independent source test. Learning uses BPM, key and the actual remaining pool; use `harmonize-learn --learner priority` for examples with labelled Key/BPM priority and nullable tolerance, retaining `--learner modes` for legacy priority-blind experiments. Compare literal Top3 on steps with at least four remaining tracks, ties and final small pools separately. A private profile assembles a complete route through `harmonize --ranking-profile`: bounded search retains alternative prefixes to the end, recomputes each actual remaining pool and normalizes conditional scores before adding them. A sequential candidate with exact small-tail bounds protects harmonic compatibility; both paths receive bounded repair. Keep original decisions separate from the selected final route. Compare directed neighbors and contiguous three/four-track chains; repeated choices with different remaining pools do not prove the same decision context. Keep local agreement, whole-route similarity and key allowance distinct. Development by intensity and bass belongs to ordinary sets, separately from BPM/key-only comparisons. Search and profiles are ours, not confirmed DJ.Studio internals; actual Solve warnings override theoretical allowance. Feed the selected order into fixed-order planning and SYNC rendering after source/timing checks.

For a requested DJ.Studio-style complete-order comparison, select packaged `--preset djstudio-route-v2`; for local next-track suggestions use `harmonize-rank --preset djstudio-next-v1` with the actual played prefix and remaining pool. Route-v2 builds a primary Density route and a Paired safety route with the same actual musical pool and explicit constraints. It selects safety only when the complete route has strictly fewer links outside the caller's harmonic table; ties retain primary. It compares neither teacher agreement nor different models' utilities. Both choices and the musical criterion are retained in `preset_route_selection`; unavoidable compromises remain disclosed. The coefficients were already frozen; this two-route safeguard was declared after diagnostics of the frozen model routes, before the complete 32-route audit, and evaluated after that audit in a separately labelled comparison. Preserve `djstudio-route-v1` for reproducing its earlier policy. These profiles show different observed tradeoffs, not a universal winner or source-independent validation. Preserve the declared mode, priority and nullable tempo tolerance. The ordinary `make` musical arc and DJ Zhilin mixing style are independent of these ordering presets; do not silently switch them. Only sanitized published parameters are bundled; new fits, examples, private profiles and reports stay private unless explicitly published.

For labelled ordering examples, keep Mood/Fuzzy, Key/BPM priority and tempo tolerance separate. The user's explicit settings override a backup filename; missing settings remain unknown. Priority-aware profiles consume these controls in both local ranking and hypothetical route states. Legacy profiles retain their earlier behavior. A fixed-parameter fit on one connected source cohort is an experimental training result, not held-out validation; save its profile privately for the next forward test.

For blocked demonstrated next tracks, compare native BPM distance with allowed alternatives before attributing the mismatch to ranking. Keep missing wizard priorities unknown; our key table is not DJ.Studio's Solve result. Report improvements in Top3 and complete routes separately, including regressions. When a new profile improves local ranking but worsens the requested whole-route agreement, retain the approved working profile and label the new profile as an experiment for the next test.

When an ordering update must preserve agreement, freeze the working baseline before fitting and compare baseline/candidate on the same references, controls, actual prefixes, literal Top3 and denominators. Preserve old-corpus and equal-control results alongside the expanded estimate; explain test-mixture changes separately. Retain the working profile if the declared regression criteria fail. Do not raise K, exclude blocked targets or condition on teacher endpoints to preserve a percentage. Known-reference checks are retrospective regression; freeze the candidate before a future forward test. Read the [Key-repeat comparison](references/benchmark-20261014-key-repeats.md) for the current baselines and position evidence.

Treat beats, downbeats and phrases as separate evidence. Beat This! predicts beats/downbeats; CUE-DETR proposes structural cues from the source spectrogram. Fuse model suggestions with structural changes and the bar grid. Preserve imported reviewed cues even when the model disagrees. Counting sixteen bars alone does not identify a phrase. Record actual model execution, hashes, uncertainty and exceptions. Read [references/engines.md](references/engines.md) for setup and fusion details.

## Default mixing

For newly built sets use F (`sync`) as the standard transition: both decks follow one integrated tempo curve and one beat phase throughout the overlap. Prefer long compatible windows, usually thirty-two bars, sixteen for large tempo changes. Reduce automatic windows when evidence or a short source requires it. Preserve reviewed montage decisions and explicit locks.

Matching BPM alone is insufficient. Main sections retain native tempo. Choose the energetic central core using structural cues and audio features; do not play a whole extended intro/outro by default or assume numbered DJ cues exist. Target 180–240 seconds of solo play between overlaps, with a hard 300-second maximum. Retain at least 120 seconds including overlaps. Short sources need shorter solo play; a small minimum deficit can use a disclosed short, stable whole-bar repeat before the exit. Never invent beats or add silence to meet a duration. Bigger deficits or conflicting locks stop the run. Report exact solo, deck and overlap durations separately. See [references/transition-preferences.md](references/transition-preferences.md).

Use separate bass, middle and high-frequency curves tied to the shared beat phase. Pass bass over four beats near the middle. Softly transfer mids over eight to sixteen beats; initially attenuate the incoming mids and avoid holding two dense mid parties together. Highs use a gentler cross throughout the overlap. Paired band gains never exceed unity. Do not compensate attenuation by raising the entire incoming deck.

Use measured bass availability when selecting automatic windows: the outgoing source should support the handoff and the incoming source should already carry bass there. Avoid bass-empty intro/outro regions while allowing short musical fills. The 35–180 Hz profile is an energy proxy, not a kick detector; reviewed quiet cues remain constraints. Check the actual rendered overlaps for energy holes before delivery.

When local Demucs estimates are available, prefer cues with less competing vocal activity and selectively hand over foreground estimates. Apply the same timing and linear preparation to mixture and voice estimates. Bypass subtraction when estimates cannot be aligned or one voice is insignificant. Stems contain leakage; inspect vocal interference in the actual result.

Refine coarse beat labels against repeated primary percussion attacks in the source, preferably with available drum estimates. Check actual rendered PCM against the shared clock and directly compare both decks throughout the overlap. A maximum measured error matters even when only one beat misses; averages and accurate mathematical anchors cannot certify coincident attacks. Missing or ambiguous measurements remain explicit coverage gaps, and zero coverage must stop delivery as verified SYNC. Re-render from original float audio, retain the best measured candidate, and apply its final map to voice estimates too. Never shorten an approved transition to conceal a timing error. Read [references/acoustic-sync.md](references/acoustic-sync.md) when diagnosing or repairing drum collisions.

Inspect coverage gaps at the user's complained-about time, even when neighbouring recognized hits pass. Distinguish backend displacement from fills and offbeat attacks already present in the source; accurate main hits do not guarantee that two percussion figures blend. Prefer another compatible entrance of the same approved length for a conflicting figure. When stretching changes a supported attack's shape, a bounded native-attack preservation fallback can retain its waveform, with identical foreground routing and fresh PCM checks. Record its local joins and uncertainty rather than promising every attack is perfectly aligned.

## Optional DJ Жилин

When a kick has a bright leading transient and a later dominant bass body, compare coherent source attack families in separate bands. Do not certify the whole attack using only the strongest bass-body template. Retain the selected band and front/body offset in provenance; weak or conflicting front evidence remains unresolved. For a reviewed percussion collision, fresh drum estimates of the final timed, foreground-processed decks can transfer the entire percussion spectrum with the bass envelope while melodic beds keep their broad mid/high curves. Never subtract estimates from an earlier timing map. Source separation is approximate: inspect the actual mixed overlap and use listener feedback ahead of reassuring template numbers.

Leading-attack verification belongs to ordinary SYNC. In DJ Zhilin, the renderer automatically requests final-deck drum estimates when a coherent earlier upper front was selected on either relevant source window; it retains broad harmonic curves while transferring percussion with the bass curve. The configured local Demucs runtime is required for that detected case. No separate skill invocation or transition flag is needed. Choosing `default_style: zhilin` makes this mode the workstation default; a fresh installation still needs engines and model weights. Do not claim automatic full-spectrum percussion routing on other styles or on unresolved front evidence.

For this detected path, verify recognized leading fronts in the actual combined waveform and retain `blended_front_audit`, including coverage and optional bounded local corrections. Deck timing alone cannot establish that the final mix passed. Preserve attack identity when comparing a shorter initial-front template view; repeat the master/export checks after a correction. See [references/acoustic-sync.md](references/acoustic-sync.md). Do not infer completion of earlier musical-set audits from this engine capability.

Use `make --style zhilin` when requested or selected by the workstation's `default_style`. Prefer thirty-two-bar compatible overlaps. Spread the middle-frequency handoff across almost the entire overlap: the incoming texture appears well before the bass handoff and the outgoing texture remains afterwards. Transfer bass slowly over about one eighth of the overlap (four bars in a thirty-two-bar transition); highs cross gently throughout. Complementary band gains prevent two full-level foregrounds. Use the configured `zhilin_profile`; [assets/zhilin-reference-v1.json](assets/zhilin-reference-v1.json) contains the approved normalized reference envelopes without source identities, cues or feedback. Its path must be recorded explicitly in private runtime config; otherwise disclose the broad fallback. Shared SYNC, vocal alignment and rendered-attack checks still apply. Preserve approved durations/cues, including forty/forty-four bars and explicit partial-bar beat counts. Source availability and protected material may require shorter overlap. This is an adaptation of the approved native reference, not a guarantee of identical sound on different music. Details are in [references/engines.md](references/engines.md).

## Sound and delivery

For the user's adaptive-middle preference, assess the actual synchronized overlap rather than whole-track key alone. Prefer up to thirty-two bars where the sources support each other harmonically and rhythmically. Preserve useful midband percussion/accompaniment over an otherwise empty kick section. Different chroma or uncertainty alone must not force a shorter handoff. Shorten smoothly for competing foreground voices, persistent discordant tones or conflicting melody parties in the same band. Diagnose low-frequency attack collisions separately: a shorter bass cross can retain the approved long middle; do not move a deck without trustworthy attack evidence. Explicit user audition overrides signal heuristics. The engine accepts per-edge `mid_handoff_bars` and `bass_handoff_beats` for DJ Zhilin while preserving the other bands. Read [references/adaptive-mids.md](references/adaptive-mids.md) and configured private `adaptive_mid_feedback` for reviewed examples. Local chroma/interval measures remain uncalibrated proxies, not pleasantness probabilities. Freeze predictions before listening feedback; preserve timing and compare only the band being tested. Training on one reviewed set does not establish accuracy on new music.

Decode originals to float PCM. Repair identified DC/noise defects selectively, use restrained content-dependent EQ, and bypass unnecessary processing. Avoid stacked aggressive per-track masters. Make one complete-set master with headroom; preserve native sample rate for single-file processing and declare set resampling.

Export explicitly configured twenty-four-bit FLAC; MP3 is an optional listening copy. Independently check the entire encoded file: decode, sample rate, channels, bit depth, duration, integrated loudness, sample peak and oversampled true peak. FLAC preserves the processed signal without another lossy encoding stage; it does not reconstruct information removed by MP3.

Deliver audio, timed track list for a set, private processing provenance and a brief verification report. Keep the user's audition/ranking separate from measurements. Compare excerpts at matched loudness. A plan or synthetic test alone is not a completed musical set.

Name ordinary folder-set outputs `YYYY_MM_DD_FolderName`, using only the date and main source folder name; do not append the track count. Preserve explicitly requested existing names and dates on revisions. Deliver only the music file and a relative-file CUE to configured `delivery_root`. Keep reports, analysis, intermediate audio and backups under `private_output_root`. CUE chapters must reflect the actual rendered starts and resolve the delivered filename. Preserve an existing version privately before an explicitly requested replacement; ordinary new runs choose a version suffix instead of overwriting.

Exclude previously used tracks during automatic folder selection using private `track_history`, seeded from the user's ready-folder CUE files and verified completed manifests. Match normalized artist/title/version and available source hashes; CUE-only history cannot identify arbitrary renamed recordings. Register only completed exports, and keep a human-readable index in `_Индекс_треков/Использованные_треки.txt`. Refresh ready-folder CUE history before selecting a new set. Preserve explicitly requested tracks and revisions; use `--allow-repeats` only when authorized. If fewer unused tracks remain than requested, explain the shortfall rather than silently repeating.

For an existing project or exported CUE/audio, read [references/djstudio.md](references/djstudio.md). The advanced preserving rewrite API changes specified fields in a new archive and checks retained members; application import and reproduction of automation remain separate checks. Keep this capability out of the ordinary one-file/many-file flow.
